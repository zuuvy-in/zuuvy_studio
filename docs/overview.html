How Zuuvy Studio works

An AI-first website builder for landing pages, portfolios and stores. It is aimed first at businesses already on Zuuvy. A business describes what it wants, the AI edits the site through validated operations, and every change is a version the owner previews before publishing. Products and orders flow to and from Zuuvy.

02 · System

Architecture

Three processes share one codebase and one database. The studio is where businesses work. The renderer serves every tenant's live site. The worker does everything that must survive a crash or wait on the outside world.

ProcessWhat it ownsScales by
apps/studioSign-in, dashboard, every mutation (server actions call requireSession() themselves), preview, export downloads, webhook receiver.1 task (AI edits are long server actions; ALB idle timeout 180 s)
apps/rendererResolves the Host to a site and renders the published version with the same runtime the preview uses. Product pages, COD order form, order tracking.2–6 tasks, CPU autoscaling
scripts/worker.tsOutbox topics: order.push, catalog.sync, domain.*, git.*, email.send.1 task; jobs claimed with SKIP LOCKED, so more is safe

03 · High-level design

Multi-tenancy: one database, isolation in Postgres

Every tenant-owned row carries tenant_id. The application connects as zsite_app, which owns nothing and cannot bypass Row-Level Security. withTenant(id, fn) opens a transaction with app.tenant_id set, and every policy reads tenant_id = app_tenant(). A query that forgets its WHERE clause returns nothing rather than another business's rows.

The few lookups that must cross tenants return ids only, through SECURITY DEFINER functions: which site a Host names, which integration a webhook names, claiming outbox jobs. The internal dashboard's functions return metadata and totals, never trees, credentials or orders.

Identity is global and membership is per tenant: one person, one login, several businesses. The same model Zuuvy's backend uses.

A site is data, not code

A site is a tree: meta, theme, nav, footer, and pages holding sections, where each section is one of 12 blocks with zod-validated props. It is changed only through applyOps: pure operations that validate the whole result or throw words the AI can act on. Beside the tree, each version holds its data: structured collections (profile, projects…) shown by collection sections.

This is what makes the product safe. An AI edit can never produce a broken page. Diffs are field-level. Templates are just trees. Versions are cheap and immutable. The brand kit can be enforced mechanically. And the whole site round-trips through source files and GitHub.

The AI agent

The agent gets the tree, the data, the brand brief, the media library and any attachments. It works through provider-neutral SiteTools, each of which validates its own input and returns errors to the model as text so it can correct itself. Bedrock's Converse API with Nova Pro is the default (AWS credits). Anthropic is a drop-in provider.

ToolsRule
view_site add_section update_section move_section add_page set_theme set_navigation …Each is one applyOps call. set_theme drops brand-fixed fields and says so.
view_data add_entry update_entry remove_entry move_entryAdditions and filling empty fields apply at once. Changing or removing existing entries becomes a proposal.
generate_imageNova 2 Omni, 4 per request, palette appended, stored in S3 and recorded as an asset.
fetch_referenceA guarded fetch of a public page, reduced to headings, sections, colours and fonts. Up to 3 per request.

The result is always a new, unpublished version. The brand kit is applied over it again as the guarantee, and every attempt, including failures, is written to ai_usage.

Async work: the outbox

Anything that calls the outside world or must survive a crash is an outbox row written in the same transaction as its cause. An order and "send it to Zuuvy" commit together or not at all. So do a version and "push it to GitHub", or an order and "email the owner". The worker claims due jobs (claim_outbox, FOR UPDATE SKIP LOCKED) and runs each inside the job's own tenant context, with backoff. A PermanentError parks the job as dead and runs its onDead.

Network calls never happen inside a database transaction. The AI agent in particular runs outside one, because it can take a minute.

AWS deployment

Two CDK stacks, deployed by GitHub Actions over OIDC with no stored AWS keys: test → ZsiteBase → migrate (one-off ECS task, which also seeds the superadmin) → ZsiteServices → a smoke test that checks /api/health reports the commit.

Flow: "describe a change"

  1. studio actiongenerateAction: session check, reads prompt, reference links (added to the prompt) and files → toAttachments (extension + magic-byte check, ≤5 × 4.5 MB).
  2. platformgenerateVersion loads the base version (tree + data), brand, catalogue categories and media library in one withTenant, then closes the transaction.
  3. platformBuilds capabilities: lockedTheme from the brand, the image palette, generateImage (if S3 is configured), fetchReference.
  4. ai · agenteditSite composes the system prompt (block + collection schemas) and the user message (facts, brand brief, media, tree, data, request). Attachments ride as Converse document/image blocks.
  5. ai · providerConverse loop: the model calls tools, and each runs applyOps / applyDataOps or records a proposal. Tool errors go back as text. It stops on final text or after 30 iterations.
  6. platformapplyBrand over the result. One transaction writes the version (tree, data, ai_meta.proposals), records the AI's colour choices, inserts ai_usage, and queues git.push if GitHub is linked.
  7. on failureThe AgentError carries the tokens already spent → an ai_usage row with outcome error / no_change / refused, and the message is shown on the form.
  8. owner, laterOn the version page: allow proposals → applyProposals applies them to the latest data as a new version.

Flow: publish, rollback and GitHub

  1. publishVersionRow-locks the site, moves published_version_id, appends site_publications, queues git.merge if linked. Rolling back is the same call with an older version.
  2. rendererThe next request resolves Host → site (definer function, www/bare twin for custom domains) and renders the published tree + data.
  3. git.pushtreeToSource → Git Data API: a tree on top of main (other repo files kept, stale page and data files removed) → commit → branch zuuvy/v<n>.
  4. git.mergeA commit whose tree is the published version, with parents [main, zuuvy/v<n>] → fast-forward main. A rollback therefore really rolls main back.
  5. import branchReads zuuvy-site.json + site/** from any branch → sourceToTree (full validation, file-level errors) → new version.

Flow: an order

  1. rendererCOD form → placeOrder: checks the site is a store and each product's source matches its inventory mode. Stock is checked unless the mode is none.
  2. same transactionThe order and its first event, plus order.push (Zuuvy lines) and one email.send per alert recipient (from alerts@).
  3. Zuuvy modeThe worker posts the order. Zuuvy confirms (stock reserved there) and sends signed webhooks. applyOrderStatus only moves forward and is idempotent by delivery id.
  4. studio modeThe owner accepts: advanceOrder takes stock with a conditional update (stock >= qty), so two acceptances cannot sell the last unit twice. Cancelling an accepted order returns the stock.
  5. customerA tracking page by unguessable token (/order/<token>).

Flow: a custom domain

  1. addDomainNormalise (punycode, no IPs or wildcards, not under zuuvy.site). Uniqueness via domain_taken. Insert as pending and queue domain.provision.
  2. provisionACM RequestCertificate (DNS validation, idempotency token = domain id), then wait until the validation record exists and save it. The studio shows both CNAMEs.
  3. check (repeating)Certificate ISSUED → AddListenerCertificates. DNS is checked via public resolvers: CNAME → domains.zuuvy.site, or matching A records. Checks run every 1 min, then every 5 min, then every 30 min, for 72 h.
  4. activeStatus active → the renderer serves it, and an email goes from no-reply@ to whoever added it.
  5. removeDelete the row and queue domain.release: detach from the listener, delete the certificate (retried while it is still in use).

Flow: export, delete, import

  1. exportA zip with the manifest (site, brand, versions index, publications, domains, orders + events), versions/NNNN.json + .data.json, current/ as source, and assets/ bytes from S3. It stamps exported_at and exported_seq.
  2. deleteRefused unless the export holds every version (exported_seq = version_seq), is under 24 h old, and the typed name matches. Certificates are released and the site row deleted. Versions and domains cascade, orders keep their rows with site_id set to null, and media stays.
  3. importZip-bomb-guarded unzip, validate every version, re-store pictures for the new tenant and rewrite their URLs, recreate the versions in order, publish the one that was live.

Read in this order

  1. packages/core/src/tree.ts
    The site schema. The .describe() texts are what the AI reads about each block.
  2. packages/core/src/ops.ts
    applyOps: the only way a tree changes. Pure, all-or-nothing, errors written for a model.
  3. packages/core/src/data.ts and brand.ts
    Collections, overwrites() (what needs permission), applyBrand.
  4. packages/platform/src/db.ts
    withTenant / withGlobal: how RLS is engaged. Read it with the policies at the bottom of 0001_init.sql.

    Versions: create (data carried forward, git queued), publish, restore with a table picker.
  6. packages/ai/src/tools.ts → agent.ts → providers/bedrock.ts
    Tools, the prompt, and the Converse loop.
  7. packages/platform/src/ai-versions.ts
    Where brand, media, capabilities, usage and proposals meet.
  8. packages/platform/src/outbox.ts + jobs.ts
    Background work, then any handler: orders.pushOrder, domains.checkDomain, git.mergeVersion.
  9. apps/studio/app/(dash)/sites/actions.ts
    Every site mutation the UI offers, each starting with requireSession().
  10. infra/lib/*.ts + .github/workflows/deploy.yml
    What runs where, and how it gets there.

Key code

RLS is engaged per transaction

// packages/platform/src/db.ts
async function transaction(tenantId, fn) {
  const client = await pool().connect();          // as zsite_app: no BYPASSRLS
  await client.query("begin");
  if (tenantId) await client.query("select set_config('app.tenant_id', $1, true)", [tenantId]);
  const result = await fn(wrap(client, tenantId));
  await client.query("commit");
  return result;
}
